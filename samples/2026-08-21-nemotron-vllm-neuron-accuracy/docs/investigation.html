technical investigation report

NemotronH on vLLM Neuron: from symptom to culprit

NemotronH on vLLM Neuron: 症状から犯人特定まで

A reproducible, component-by-component investigation of an on-device reasoning failure -- what it ruled out, what it could not yet isolate, and the decisive experiments left to run.

on-device での推論崩壊について、部品単位で再現可能な調査を行った記録 -- 何を排除できたか、何がまだ単離できていないか、そして残された決定実験。

Model: nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 · Plugin: vllm-project/vllm-neuron · Neuron SDK 2.31.0 / 2.32.0 · Hardware: trn2.3xlarge

対象モデル: nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 · Plugin: vllm-project/vllm-neuron · Neuron SDK 2.31.0 / 2.32.0 · ハード: trn2.3xlarge

One-line summary. A hybrid Mamba2/MoE/Attention decoder answers correctly on CPU and on a CUDA GPU, but produces a deterministic (byte-identical) wrong output on multi-step arithmetic reasoning when served through the vLLM Neuron plugin on Trainium, while short factual completions and long-range recall stay correct. Nine independent experiments rule out the model, bf16 precision, single-operator precision, the Trainium hardware, the neuronx-cc compiler version, the plugin's own compiler flags, and each individual kernel tested standalone (Mamba2 scan, MoE router) — but every one of those experiments also changed at least one other variable versus the real failure, so none of them validly isolates a single culprit. What is established is that the fault sits in a shared code path above kernel selection; which component in that path is still an open question — see the Established / Open summary below.

一言まとめ。 Mamba2/MoE/Attention のハイブリッドデコーダは CPU と CUDA GPU では正答するが、Trainium 上で vLLM Neuron plugin を経由すると多段の算数推論で決定的 (byte 単位で同一) な誤出力を返す。短い事実応答や長距離 recall は健全なまま。9 個の独立した実験で、モデル・bf16 精度・単一演算の精度・Trainium ハード・neuronx-cc の版・plugin 独自のコンパイラフラグ・単体で検証した各カーネル (Mamba2 scan・MoE router) を無罪にしたが、これらの実験はいずれも実際の失敗構成に対し他の変数も同時に変えており、単一の犯人を妥当に単離してはいない。確定しているのは故障がカーネル選択より上流の共有コードパスにあることだけで、そのパスのどの部品かは依然未解決 -- 下記の Established / Open のまとめを参照。

Established vs. open -- read this first

確定していること / 未解決のこと -- まず読むべき箇所

Established (confirmed by direct experiment):

  • The plugin path produces a deterministic, byte-identical wrong output; the identical graph is correct on CPU and on GPU.
  • The failure is task-selective: multi-step, order-dependent, and arithmetic reasoning collapse; short factual completions and long-range verbatim recall survive.
  • Byte-identical output across two different scan algorithms and two different attention-kernel prefill paths localizes the fault to a shared code path above kernel selection and rules out non-deterministic numerical drift.
  • An FP8 sibling model still answers correctly on GPU, independently ruling out mechanisms that are sensitive to small numerical perturbations.
  • On the failing prompts, the first generated token is already wrong -- the defect is visible at prefill/logit time, not only after several decode steps.

Open (not established):

  • Which component inside that shared path is at fault. Every exonerating experiment below changed two or more variables versus the real failing configuration (plugin frontend, 52 layers, MoE, autoregressive decode) at once, so no single stage -- including full-graph compilation -- has been validly eliminated or convicted. See Section 2 for the variable-confound detail, Section 2b for the ranked live candidates, and Section 4 for the next decisive experiments.

確定していること (直接実験で確認済み):

  • plugin 経路は決定的 (byte 単位で同一) な誤出力を返す。同一グラフは CPU・GPU では正しい。
  • 故障はタスク選択的: 多段・順序依存・算数推論は崩壊するが、短い事実応答や長距離の逐語 recall は健全。
  • 2 種類の scan アルゴリズムと 2 種類の attention カーネル prefill 経路を跨いで出力が byte 単位で一致する -- 故障をカーネル選択より上流の共有コードパスに局在させ、非決定的な数値ドリフトを排除する。
  • FP8 の姉妹モデルは GPU で正答する -- 微小な数値摂動に敏感な機構を独立に排除する。
  • 失敗するプロンプトでは最初の生成トークンが既に誤っている -- 故障は数ステップの decode を経てからでなく、prefill/logit の時点で既に見えている。

未解決 (確定していないこと):

  • その共有パスのどの部品か。以下の各無罪実験は、実際の失敗構成 (plugin frontend・52 層・MoE・自己回帰 decode) に対して 2 つ以上の変数を同時に変えている。そのため full-graph コンパイルを含め、どの段も妥当に「排除」も「有罪」もできていない。交絡の詳細は 2 節、有効な候補ランキングは 2b 節、次の決定実験は 4 節を参照。

1. The system: what runs where

1. 全体像 -- 何がどこで動くか

NemotronH interleaves three layer types across 52 layers and carries positional information only through the Mamba2 recurrence (NoPE — no explicit positional encoding such as RoPE). The diagram below is the key piece of evidence in this whole investigation: the same model, same weights, and same input are pushed through four execution paths. Two of those paths run on the exact same hardware and the exact same neuronx-cc compiler version — yet only one of them breaks.

NemotronH は 52 層にわたって 3 種類の層を交互に配置し、位置情報は Mamba2 の再帰計算だけが運ぶ（NoPE = RoPE 等の明示的な位置エンコーディングを持たない）。下の図はこの調査全体で最も重要な証拠。同じモデル・同じ重み・同じ入力を 4 つの実行経路に通した。うち 2 つは全く同じハードウェア・全く同じ neuronx-cc の版で動くのに、片方だけが崩壊する。

2. The elimination path

2. 犯人特定までの消去法

Every plausible suspect was tested directly, one at a time. Each individual test came back clean -- but, as the annotations below make explicit, every one of those tests also changed at least one other variable versus the real failing configuration (the plugin's own frontend, 52 layers, MoE, autoregressive decode). That means the chain below is not a valid elimination proof for any single stage; what it validly establishes is only the two terminal boxes (fault above kernel selection; component still open). See §2b for how the remaining candidates rank against all the evidence, and §2c for a mechanism this investigation proposed and then rejected using its own data.

考えられる容疑者を一つずつ直接実験にかけた。個々のテストはいずれも「無罪」で返ってきたが、下の各注記が示す通り、そのテストはいずれも実際の失敗構成 (plugin 自身の frontend・52層・MoE・自己回帰 decode) に対して他の変数も同時に変えている。つまり以下のチェーンは、どの単一段に対しても妥当な消去法の証明ではない。妥当に確定しているのは終端の 2 つのボックス (故障はカーネル選択より上流／部品は未解決) のみ。残る候補の証拠との整合度は 2b 節、提案してから自ら却下した機構は 2c 節を参照。

2c. Rejected hypothesis: compounding MoE router-selection flips

2c. 却下した仮説: MoE router 選択の複利的な flip

An earlier draft of this investigation proposed that tiny per-layer numeric differences compound across the model's 23 stacked MoE layers, flipping which experts get selected, and that this was the mechanism behind the break. This mechanism is rejected -- it is directly contradicted by two pieces of evidence already in this report:

本調査の初期の草稿では、モデルの 23 段の MoE 層を跨いで層ごとの微小な数値差が複利的に増幅し、選ばれる expert が flip することが崩壊の機構だと結論していた。この機構は却下する -- 本レポート中の 2 つの証拠と直接矛盾するため。

  • The FP8-on-GPU sibling uses a perturbation orders of magnitude larger than bf16 rounding noise, and still answers correctly. If tiny flips in expert selection caused total failure, FP8 should be catastrophic on GPU. It is not.
  • The wrong output is byte-identical across two scan algorithms and two attention-kernel prefill paths. Numerical noise compounding is exquisitely sensitive to summation order; changing kernels changes rounding patterns and should change the output bytes. Byte-identical failure indicates a deterministic bug in a shared path, not chaotic noise accumulation.
  • FP8 の姉妹モデルは bf16 の丸め誤差より桁違いに大きい摂動を持つにもかかわらず GPU で正答する。微小な expert 選択の flip が全面的な崩壊を引き起こすなら、FP8 は GPU 上で破滅的になるはずだが、そうならない。
  • 誤出力は 2 種類の scan アルゴリズムと 2 種類の attention カーネル prefill 経路を跨いで byte 単位で一致する。数値ノイズの複利増幅は加算順序に極めて敏感で、カーネルを変えれば丸めパターンが変わり出力の byte も変わるはず。byte 一致の崩壊は、カオス的なノイズ蓄積ではなく共有パスの決定的バグを示す。

The supporting experiment for this mechanism -- feeding a synthetic 23-layer stack of the standalone router forward with an arbitrary coupling function and observing 8/256 token selections flip -- does not rescue it: the coupling has no relationship to the model's real inter-layer transfer function (expert MLPs, residuals, and norms typically damp perturbations rather than amplifying them arbitrarily); no CPU-vs-GPU baseline was run for the same synthetic stack, so it is unknown whether ordinary bf16 rounding differences would also flip a similar number of selections on hardware that works fine; and the experiment assumes the conclusion (that flips matter) in order to support it. It is kept here as a documented dead end, not as evidence for candidate #4 above.

この機構を支持するために行った実験 -- router 単体を任意のカップリング関数で 23 段合成的にスタックし、256 トークン中 8 トークンの選択が flip するのを観測したもの -- もこれを救わない。カップリングはモデルの実際の層間伝達関数 (expert MLP・residual・norm は通常摂動を任意に増幅せず減衰させる) と無関係であり、同じ合成スタックで CPU-vs-GPU のベースラインが取られていないため通常の bf16 丸め誤差でも正常に動く GPU 上で似た数の flip が起きるかは不明であり、さらにこの実験は「flip が重要だ」という結論を前提として組まれている (循環論法)。ここでは上記候補 #4 の証拠としてではなく、記録済みの dead end として残す。

4. What could not be pinned down from outside the plugin -- and the next decisive experiments

4. plugin の外からは特定できなかったこと -- そして次の決定実験

The investigation reached a hard limit on external tooling before it could point at a single line of code inside the plugin's compile path. Three attempts to look further were each blocked by an unrelated tooling constraint rather than by the underlying bug itself:

plugin の compile 経路内の一行まで特定する前に、外部ツールの限界に達した。さらに深く見るための 3 つの試みは、いずれも本来のバグとは無関係なツール制約に阻まれた。

  • A layer-by-layer activation dump (the plugin's own accuracy-debugging facility) did not produce any output, because the model's serving-optimized forward pass (which returns only logits) does not route through the dump mechanism's expected output path.層ごとの活性ダンプ (plugin 公式の精度デバッグ機構) は出力ゼロだった。serving 用に最適化した forward (logits のみ返す) がダンプ機構の想定する出力経路を通らないため。
  • Compiling the full, untruncated 52-layer graph through the standard AOT frontend produced a NEFF too large to load onto a single NeuronCore (an allocation failure unrelated to correctness).52 層フルグラフを標準 AOT フロントエンドでそのままコンパイルすると、NEFF が単一 NeuronCore に載らない (正誤とは無関係な allocation failure)。
  • A minimal synthetic configuration built to isolate the hybrid pattern crashed the compiler frontend natively (a memory-corruption crash unrelated to correctness), forcing the investigation to use a truncated slice of the real model instead.hybrid pattern を単離するための最小合成構成は、コンパイラフロントエンドで native crash (正誤とは無関係なメモリ破損) を起こし、実モデルの truncate 版で代替する必要があった。

The next decisive experiments (in order)

次の決定実験 (実施順)

B (run first, nearly free). Greedy-decode a failing arithmetic prompt and diff the logits against CPU at every step, recording the first divergent step. This changes zero variables and splits the whole remaining hypothesis space in two: divergence already at the first generated token points at prefill/compile/weights (this investigation's own data already shows this: the first token is wrong); divergence only at step ≥2 would point at decode/state-handoff. Refinements: also run full-prefill vs. incremental-decode on-device only (no CPU needed) as a self-consistency check, and dump the recurrent state immediately after prefill if the plugin's instrumentation allows it.

A (choose the variant based on B). Build a layer-truncated prefix of the real 30B model that includes at least one full MoE layer (router + dispatch + expert GEMMs + combine), compiled through the plugin's own frontend (not the standard trace API), and compare against CPU. This is the first experiment that would cross the confounds documented in Section 2 -- plugin frontend, real MoE, at a traceable size.

C (cheap, run in parallel). Bisect the SDK 2.31→2.32 changelog against this reproduction. A partial fix means the vendor already touched the guilty code; the fix's diff is a free localization signal.

B (最優先・ほぼ無料)。 失敗する算数プロンプトを greedy decode し、毎ステップの logits を CPU と差分して最初に発散するステップを記録する。変数を一切変えず、残る仮説空間全体を二分できる: 最初の生成トークンから既に発散していれば prefill/compile/weights 側を指す (本調査のデータは既にこれを示している -- 最初のトークンが誤り)。step≥2 でのみ発散するなら decode/state-handoff 側を指す。追加案: device 内だけで full-prefill vs 逐次 decode の self-consistency チェック (CPU 不要)、plugin の計測機構が許せば prefill 直後の再帰 state をダンプする。

A (B の結果に基づいて選択)。 実際の 30B モデルから、完全な MoE 層 (router + dispatch + expert GEMM + combine) を最低 1 つ含む layer-truncated prefix を構築し、標準の trace API でなく plugin 自身の frontend でコンパイルして CPU と比較する。2 節で記録した交絡 (plugin frontend・実 MoE) を trace 可能なサイズで初めて跨ぐ実験になる。

C (安価・並行実施)。 SDK 2.31→2.32 の changelog を本 repro と突き合わせて bisect する。部分的に修正されたということは、vendor が既に該当コードに触れている可能性が高く、その修正差分は無料の局所化ヒントになる。

5. Confidence levels

5. 確度の区分

Confirmed確定 -- reproduced by a direct experiment -- 実験で直接再現・確認 Strong inference強い推論 -- directly supported by independent evidence, not a full elimination proof -- 独立した証拠に直接支持されるが、完全な消去法の証明ではない Open question未解決 -- no candidate has positive evidence yet -- どの候補にもまだ直接の証拠が無い Rejected却下 -- proposed, then contradicted by this investigation's own evidence -- 提案したが本調査自身の証拠と矛盾したため却下

The claim "the fault is a deterministic bug in a shared code path above kernel selection" is a strong inference supported directly by two independent facts: byte-identical wrong output across different scan and attention kernels, and a lower-precision (FP8) sibling that still works on GPU. It is not a full elimination proof, because none of the per-component isolation experiments held every other variable fixed (Section 2). The claim "which specific component is responsible" is an open question, not yet a hypothesis with supporting evidence -- Section 2b ranks the live candidates by how well each explains all the evidence, and none of them has positive evidence yet. One candidate mechanism this investigation proposed earlier (compounding MoE router-selection flips) was tested further and is now a rejected hypothesis (Section 2c): it is directly contradicted by the FP8-on-GPU and byte-identical evidence already used to support the strong inference above.

「故障はカーネル選択より上流の共有コードパスにある決定的なバグである」という主張は、2 つの独立した事実 -- 異なる scan/attention カーネルを跨いで byte 単位で一致する誤出力、および GPU では動く低精度 (FP8) の姉妹モデル -- に直接支持される強い推論である。ただしこれは完全な消去法の証明ではない。部品単位の単離実験はいずれも他の変数を固定していないため (2 節)。「具体的にどの部品が原因か」という主張は、根拠のある仮説の段階にすら達していない未解決の問いである -- 2b 節で有効な候補を全証拠との整合度でランキングしているが、いずれもまだ直接の証拠は無い。本調査が以前に提案した機構の一つ (MoE router 選択の複利的な flip) はさらに検証した結果、現在は却下した仮説である (2c 節) -- 上記の強い推論を支持する FP8-on-GPU と byte 一致の証拠そのものと直接矛盾するため。
